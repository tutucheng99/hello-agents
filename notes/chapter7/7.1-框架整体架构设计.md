# 7.1 框架整体架构设计

## 核心要点

### 为什么要自建框架（而不是直接用 LangChain 等）
1. **现有框架的痛点**：过度抽象（Chain/Agent/Tool/Memory/Retriever 一堆概念）、API 频繁变更、黑盒难调试、依赖重易冲突。
2. **能力跃迁**：从"使用者"变"构建者"，真正理解 Agent 的思考循环和工具调用机制。
3. **定制需求**：垂直领域（金融/医疗）的提示词、安全策略；生产环境对延迟、内存、并发的精细控制。

### HelloAgents 的四个设计理念
| 理念 | 一句话 |
|---|---|
| 轻量 & 教学友好 | 代码量小到能完整读懂；依赖只有 OpenAI SDK + 少量基础库 |
| 基于标准 API | 以 OpenAI 接口为统一标准，不另造抽象 → 换模型只换 `base_url` / `api_key` |
| 渐进式学习 | 每章一个可 pip 安装的版本（本章 `hello-agents==0.1.1`） |
| 万物皆工具 | 除 Agent 外，Memory、RAG、RL、MCP 都抽象成 Tool，核心逻辑只剩"Agent 调用工具" |

### 分层架构（分层解耦、职责单一、接口统一）
```
core/    核心层：Agent 基类、LLM 统一接口、Message、Config、异常
agents/  实现层：SimpleAgent / ReActAgent / ReflectionAgent / PlanAndSolveAgent
tools/   工具层：Tool 基类、Registry 注册、工具链、异步执行、内置工具
```
依赖方向：`agents → core`，`agents → tools`；core 不依赖上层。新增一种 Agent 范式 = 在 agents/ 里继承基类，不改 core。

## 面试题

**Q1. 你为什么要自己写 Agent 框架，而不是直接用 LangChain？**
<details><summary>参考回答</summary>

先肯定现有框架（生态全、上手快），再说痛点：抽象层多导致调试困难、版本变更频繁、依赖重；然后说自建的收益：完全掌控 prompt 和执行循环、可针对业务优化延迟/成本、方便做可观测性。最后补一句务实判断：**原型阶段用成熟框架，核心链路需要精细控制时自建或只用其底层组件**——面试官更喜欢有权衡的回答，而不是"框架都不好"。
</details>

**Q2. 为什么基于 OpenAI 兼容接口来设计 LLM 层？有什么风险？**
<details><summary>参考回答</summary>

好处：几乎所有厂商（DeepSeek、通义、智谱、ModelScope）和本地推理服务（vLLM、Ollama）都提供 OpenAI 兼容接口，一套代码通吃，切换模型只改配置。
风险：各家"兼容"程度不一——function calling / tool_choice、流式格式、`max_tokens` 等参数支持有差异；厂商特有能力（如 Anthropic 的 prompt caching、推理模型的 thinking 字段）可能无法通过统一接口使用。应对：在 LLM 层做适配/降级，并对关键能力做测试。
</details>

**Q3. "万物皆工具"的设计有什么优缺点？**
<details><summary>参考回答</summary>

优点：概念少、接口统一（都是 name + description + 参数 + run），Agent 只需一个循环处理所有能力，扩展新能力只要写一个 Tool。
缺点：Memory 这类能力往往需要**每轮自动发生**（如自动检索相关记忆注入上下文），如果做成工具就依赖模型"想起来去调用"，可能漏调；工具多了以后描述占用上下文、模型选错工具的概率上升。所以实际系统常把"必然发生的"做成框架内置流程，把"按需发生的"做成工具。
</details>

**Q4. 一个 Agent 框架最少需要哪几个核心模块？**
<details><summary>参考回答</summary>

LLM 调用层（统一接口、重试、流式）、消息/历史管理、Agent 执行循环（思考→行动→观察→终止条件）、工具系统（描述 + 注册 + 执行 + 错误处理）、配置。进阶再加：记忆、规划、可观测性（日志/trace）、安全护栏。
</details>
